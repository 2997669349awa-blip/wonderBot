POSITIONING

为什么是「能力 fork」，不是又一个换皮

上游是「全平台 × 全模型 × 上千插件」的通用框架，覆盖面极广、迭代很快。 拼覆盖面必输，拼垂直深度才有位置。因此路线选的是 B：能力 fork—— 不动框架架构，只在官方还浅的地方补齐能力，并保持能持续合并上游。

第一版聚焦中文社群与私域运营：入群欢迎、问答沉淀、违规提醒、定时播报、多群汇总， 这些成套闭环官方没有做；而成本、记忆、权限三类能力是任何场景长期运行都绕不开的地基。

从 Releases 下载源码安装包并解压，或直接克隆仓库。

在配置文件写入允许的 QQ 号，然后启动主程序与 WebUI。

curl -L -o wonderbot.zip \

# 填入允许的 QQ 号：data/cmd_config.json
#   platform_settings.wonderbot_sender_allowlist.qq_ids
.venv/bin/python main.py

FAQ

常见问题

和 AstrBot 官方是什么关系？

独立衍生作品，采用 AGPL-3.0-or-later，基线为上游 v4.29.4。原始版权声明与许可证全文原样保留，修改清单写在 NOTICE.md。与上游官方团队没有隶属、背书或代理关系，也不使用其更新服务。

为什么装好后所有 QQ 命令都没反应？

这是刻意的安全默认值：白名单默认开启且 qq_ids 为空，即拒绝全部 QQ 用户命令。在 data/cmd_config.json 的 platform_settings.wonderbot_sender_allowlist.qq_ids 填入允许的 QQ 号后即可生效。被拒绝的事件在进入大模型前终止，不消耗 token。

会不会偷偷上报数据或检测到官方更新？

不会。匿名统计默认关闭；更新检查、核心包与 WebUI 包下载地址都改为自有配置，且未配置发布源时直接禁用，不发起任何网络请求。公告地址也指向本项目官网。

为什么代码里还保留 astrbot 包目录和类名？

那是 astrbot.api 插件契约层。全仓库数百个标识符与上千个第三方插件依赖这些名字，字面全替换会直接让项目跑不起来并和插件生态断链。产品可见层（界面、图标、文档、日志、环境变量、更新源）已全部为 WonderBot；AGPL 也不要求改内部标识符，只要求保留版权声明并标明修改。

有安卓 APK 吗？装上就能直接跑机器人吗？

官方 WonderBot 是 Python 服务端，本身没有 APK。我们另做了 WonderBot for Android（基于第三方移植版二创，MIT）。 本次 beta0.1.0 的 APK 真能安装、能打开原生管理界面，但属于 bootstrap 变体，不含约 1 GiB 的 ARM64 运行镜像，装完还不能立刻跑机器人； 内置完整环境、装上即用的 bundled 包需要 ARM64 root 等环境现场构建，步骤写在 Android 仓库的 BUILD_WONDERBOT.md。这一点如实说明，不假装已经做到。

可以用于商业项目或收费服务吗？

AGPLv3 允许商业化与收费（部署托管、企业定制、技术支持），但衍生作品必须继续以 AGPL-3.0-or-later 开源，不能改成 MIT、Apache 或闭源，也不能对下游附加「禁止商用」之类的额外限制。若以网络服务形式提供，须依第 13 条主动向使用者提供对应源码的获取途径。
